# 接口

这份文档描述仓库里已经提交的文件。属性名、函数参数和更新列表都以这些文件为准。

## 1. Flake 输出

`flake.nix` 只有一个输入：

```nix
inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-26.05";
```

`outputs` 的参数是 `{ self, nixpkgs }`。系统只有 `x86_64-linux`。导入 nixpkgs 时设置了 `config.allowUnfree = true`，这样本 flake 的 `packages` 和 `checks` 可以求值专有包。

| 输出 | 内容 |
| --- | --- |
| `packages.x86_64-linux.<name>` | `default.nix` 里的每个属性。名字见下一节 |
| `overlays.default` | `final: prev:`，等于 `import ./default.nix { pkgs = prev; }`。`overlay.nix` 是同一份函数，flake 直接把逻辑写在 `flake.nix` 里，`overlay.nix` 给非 flake 的 `import` 用 |
| `checks.x86_64-linux.package-<name>` | 和 `packages.x86_64-linux.<name>` 是同一个 derivation。`<name>` 里的连字符保留，例如 `checks.x86_64-linux.package-grok-bot` |

没有 `nixosModules`，也没有 devShell。

给同样钉在 nixos-26.05 的配置引用：

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-26.05";
    nur-packages.url = "github:JimmyWang0417/nur-packages";
    nur-packages.inputs.nixpkgs.follows = "nixpkgs";
  };

  outputs = { nixpkgs, nur-packages, ... }: {
    nixosConfigurations.orion = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        ({ pkgs, ... }: {
          nixpkgs.config.allowUnfree = true;
          nixpkgs.overlays = [ nur-packages.overlays.default ];
          environment.systemPackages = [ pkgs.animeko pkgs.alder pkgs.crm ];
        })
      ];
    };
  };
}
```

`nixos-config` 里对应的位置是 `flake.nix` 的 `inputs`，以及某个 NixOS module 的 `nixpkgs.overlays`。专有包不打开 `allowUnfree` 时，overlay 一应用就会在求值阶段失败。

单包构建不经过系统配置：

```bash
nix --extra-experimental-features 'nix-command flakes' build --no-link .#animeko
```

`--no-link` 避免在主目录留下 `result` 符号链接。

## 2. Overlay 里的包

`default.nix` 的签名是 `{ pkgs }:`。它只做 `pkgs.callPackage ./pkgs/<name> { }`。overlay 把 `prev` 传进这个 `pkgs`。包函数自己的参数由 `callPackage` 从 nixpkgs 填入，下面每一节的花括号就是那个函数的完整参数表。

### alder

- 文件：`pkgs/alder/default.nix`
- 参数：`{ lib, buildNpmPackage, fetchFromGitHub }`
- 版本：`2.0.0`
- 安装的程序：`$out/bin/alder`
- 运行时依赖：`nodejs`（`buildNpmPackage` 把它放进 `buildInputs`）
- 没有包进去的东西：不跑 `jest`（`dontNpmBuild = true`）。没有手册页。AUR 的 `npm install -g` 不会在构建机上再访问 registry
- 构建：`nix build --no-link .#alder`
- 系统包：`environment.systemPackages = [ pkgs.alder ];`

AUR `alder` 的安装命令就是这个 npm 包：`depends` 为 nodejs，源是 `registry.npmjs.org/@aweary/alder`。仓库没有 `Cargo.toml`，所以不是 Cargo 程序。这里用 `buildNpmPackage`。`pkgs/alder/package-lock.json` 在 `postPatch` 里复制进源码树，因为 GitHub tag 只有 `yarn.lock`。

## 3. 再加一个包

1. 新建 `pkgs/<name>/default.nix`。这个文件是一个函数，参数由 `callPackage` 注入。现有包都不是 `pkgs: { ... }` 那种一层函数。
2. 在 `default.nix` 加一行：

```nix
<name> = pkgs.callPackage ./pkgs/<name> { };
```

`callPackage` 的调用形式固定是 `pkgs.callPackage ./pkgs/<name> { }`。花括号是留给显式覆盖的，现在每个包都传空集。包函数的形参必须是 nixpkgs 里已有的名字，例如 `{ lib, stdenv, fetchurl }: stdenv.mkDerivation { ... }`。

3. 不需要改 `overlay.nix` 或 `flake.nix`。两者都是 `import ./default.nix { pkgs = ...; }`，新属性会同时出现在 `packages.x86_64-linux.<name>`、`overlays.default` 和 `checks.x86_64-linux.package-<name>`。
4. `.github/workflows/ci.yml` 不写死包名。它求值 `packages.x86_64-linux` 的全部属性名，再 `nix build`。新包只要出现在 `default.nix` 里就会被 CI 构建。
5. 周更不会自动跟上。要跟上，必须再往 `updates.nix` 的列表里加一项。见下一节。

`final: prev:` 只出现在 overlay。包函数不要写成 `final: prev:`。

## 4. 更新接口

允许被周更的包只写在 `updates.nix`。这是一个 Nix 列表，每一项都是字符串字段：

| 字段 | 含义 |
| --- | --- |
| `attribute` | flake 属性名，例如 `animeko` |
| `file` | 要改写的 nix 文件，相对仓库根 |
| `owner` / `repo` | GitHub 仓库 |
| `kind` | `github-asset` 或 `github-source` |
| `asset` | `github-asset` 的文件名。`{version}` 会被替换。`github-source` 留空字符串 |

当前列表：

| attribute | kind | 版本从哪来 |
| --- | --- | --- |
| `animeko` | `github-asset` | `ani-{version}-linux-x86_64.appimage` |
| `botmux` | `github-asset` | `botmux-linux-x64` |
| `xjtutoolbox` | `github-asset` | `XJTUToolbox-linux-x86_64.AppImage` |
| `xjtu-course-genius` | `github-asset` | `XJTU-Course-Genius-linux-x64.deb` |
| `crm` | `github-source` | tag `v<version>` 的 `fetchFromGitHub`，并重写 `pkgs/crm/Cargo.lock` |

`alder`、`easyconnect`、`grok-bot` 不在列表里。`alder` 的版本在 npm，不是 GitHub Release 附件。`easyconnect` 的 deb 不在 GitHub Release 上。`grok-bot` 的 URL 里有 Cursor 的 commit，不是 `v<version>` 这种附件名。

`.github/workflows/update.yml`：

- 触发：`workflow_dispatch`，以及每周一 04:17 UTC（`17 4 * * 1`）
- 权限：`contents: write`、`pull-requests: write`，用默认 `GITHUB_TOKEN`
- 输入：仓库工作树，以及 `updates.nix`
- 步骤：`cachix/install-nix-action@v31`，然后 `python3 ./scripts/update.py`
- `scripts/update.py` 用 `nix eval --file ./updates.nix --json` 读列表。对每一项请求 `https://api.github.com/repos/<owner>/<repo>/releases/latest`，去掉 tag 开头的一个 `v` 得到版本。版本没变就跳过
- `github-asset`：`nix-prefetch-url` 下载 `https://github.com/<owner>/<repo>/releases/download/v<version>/<asset>`，把该文件里第一处 `version = "..."` 和第一处 `hash = "sha256-..."` 换成新值
- `github-source`：`nix flake prefetch github:<owner>/<repo>/v<version>` 得到源码哈希，同样替换第一处 `version` 和 `hash`，然后在该 tag 上跑 `cargo generate-lockfile`，覆盖旁边的 `Cargo.lock`。`crm` 没有单独的 `cargoHash`，因为 `cargoLock.lockFile = ./Cargo.lock`
- 输出：工作树里被改过的 nix 文件和可能的 `Cargo.lock`。没有改动时脚本打印 `no version changes`，工作流结束
- 有改动时，工作流新建分支 `update/weekly-<UTC 时间戳>`，提交，`git push -u origin` 这个新分支，再用 `gh pr create` 对 `main` 开 pull request。命令里没有 `--force`。同一天再跑会用新的时间戳，不会覆盖旧分支

新包要加入周更，就在 `updates.nix` 追加一项。`kind` 只能是上面两个字符串。`github-asset` 的 nix 文件必须正好有一处 `version = "..."` 和一处 `hash = "sha256-..."`，否则脚本退出非零。

## 5. 故意不是输入的东西

这些不会出现在 `flake.nix` 的 `inputs`、`default.nix` 或 `updates.nix` 里：

- 密钥、age key、`.directory`、`.env`
- 原样复制的 AUR PKGBUILD
- `udf-http-range-proxy`
- `keepassxc-unlock`
- `verilog-format`
- `typora-free-with-plugin`、`typora-crack`、`typora-unlock`
- `github:Hobr/my-nix` 整份 flake
- `github:jarod/easyconnect-nix` 的 nixpkgs 18.03
- x12w 仓库里提交的 EasyConnect deb 和 `legacy-libs`
- Anaconda 安装器脚本本体
- 华为云会议的 arm64 deb 和山东大学镜像包
